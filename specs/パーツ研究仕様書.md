## 1. パーツDB

**上位N位の記事ではなく、全パーツを網羅するデータベースとする**（2026-09-17・CEO判断）。

- 置き場：`ベイブレードAI/parts_db/<種別>/<名称>.md`（`DATA_DIR` 配下）
- **名簿は `parts.csv` を使う。** パーツ名の唯一の正であり（『質問箱ワークフロー仕様書』§1 ①.0.4）、
  自前の名簿を作ると表記が割れる。全**263件**
- **1パーツ1ファイルとする。** grepでファイルを特定し、そのファイルだけ読めば済む形にするため。
  「全文をコンテキストに読み込まない」規律（同仕様書§1 ①.0）をDBでも守れる
- `parts_db/index.csv` に全件の状態を集約する。生成は `ベイブレードAI/tools/parts_db.py`。
  **既存ファイルを上書きしない**ので、育った後に再実行してよい
- 個別パーツに属さない知見（ラチェットの刃数・高さなど）は `parts_db/_shared/` に置き、
  各パーツのファイルから参照する
- **263件全件を分母とし、対象外のパーツを作らない**（2026-09-17・CEO判断）。断言台帳に一度も
  出ないコラボ系（BXC 19件）や旧世代も含める。分母を競技系だけに絞ると `parts.csv` との1対1が
  崩れ、名簿の唯一性が失われるためである
- 着手順は `ベイブレードAI/tools/parts_coverage.py` が出す。**被参照が多く、かつ材料が既にある
  パーツから埋める**。網羅率を均等に上げにいかない

### 1.1 ファイルの構造

frontmatter に `type` `name` `hud` `aliases` `status` `maxLabel` `updated` `sources`、
本文に次の節を置く。

| 節 | 何を書くか |
|---|---|
| 公称スペック | タカラトミー公式の公称値。**未取得のうちは空欄のまま。推測で埋めない** |
| 観察 | **見たままの事実。出典を必ず付ける** |
| 解釈 | なぜそうなるか。物理で説明できるものは【物理推論】 |
| 収録商品 | |
| 相性・サンプルカスタム | |
| 未解決 | 次に一次ソースを当たるべきこと |

**観察と解釈を分けるのは、出典の射程が違うからである。**
動画が示すのは「そう見えた」までであって、「なぜそうなるか」ではない。

### 1.2 status

| 値 | 意味 |
|---|---|
| `未着手` | 骨格だけ |
| `移送済` | 既存マニュアルの本文を運んだ。**主張ごとの確度ラベルは未付与** |
| `下書き` | 書きかけ |
| `記載済` | 確度ラベルまで付いて完成している |

**`移送済` を `記載済` と同一視しない。** 移送した本文は主張ごとの出典を持たないため、
そのまま断言の根拠にはできない。ラベル付けは、研究室がそのパーツを次に触るときに主張単位で行う。

### 1.3 複数ソースでの数値の食い違い【v1.2新設】

国内ブログ・海外Wiki等、二次情報源間で数値（攻撃力・重量等）が食い違う場合、
安易に一つを採用・平均化せず、**出典ごとに数値を並記**した上で「一次ソース（パッケージ表記等）
での確認を推奨」と明記する。公称スペック節は一次ソース確定分のみとし、
二次情報の食い違いは「観察」節に出典付きで両論併記する。

## 2. 確度の昇格規則

パーツDBは**CEO承認をゲートにせず、研究室が直接更新する**（2026-09-17・CEO判断）。
承認をゲートにしない代わりに、**確度ラベルをゲートにする。**

| 出典 | 書ける上限 |
|---|---|
| YouTube・レビュー記事・フォーラム（＝SNS二次情報） | **【未確認】まで** |
| 独立した2ソース以上で一致 | 【仮説】 |
| 公式スペック・一次ソース・実測 | 【確認済み（出典）】 |

**研究室は【確認済み】を自力で付けられない。** 付くのは公式スペックを取得したときか、
CEOが一次情報を入れたときだけである。

理由は『質問箱ワークフロー仕様書』§1の「SNS二次情報だけで【確認済み】を付けない」と
§4「一次ソース未確認事項の断言」の禁止にある。**ここを緩めると二次情報が正本に化け、
質問箱フローが§1①-cでそれをgrepする。** グローリーワルキューレ事故（2026-08-18）と
同じ経路が、今度は構造的に開く。

**同一人物・同一チャンネルの複数動画は「独立した2ソース」ではない。**
出典が分かれていても観測者が同じなら、系統誤差は分かれない。

### 2.1 断言台帳からの転記【2026-09-17新設】

断言台帳は公開済みの回答・記事に由来する断言であり、**主張ごとに確度ラベルが既に付いている**。
パーツDBへ転記してよい。§5が禁じているのは逆方向（パーツDB→断言台帳）である。

2026-09-17時点で、263件中185件が台帳に何らかの材料を持つ。**未着手248件の大半は
「材料が無い」のではなく「まだ運んでいない」だけである。**

- **ラベルは台帳のものを継承する。** 台帳で【確認済み】なら転記後も【確認済み】でよい。
  研究室が自力で昇格させたことにはならないので、§4-2の停止対象にもならない
- **【2026-09-18追加】備考に `[parts_db由来]` を含む行は転記しない。**
  §6で開いた逆方向によって台帳に入った行であり、**パーツDBの記述が一周して戻ってきただけである。**
  転記すれば自分の記述を自分の裏付けにすることになる。
  **「独立した2ソース」の1つにも数えない**（→ §6.2）
- 出典欄には台帳の出典記事名と公開日を書く
- **①-a.1の既知の矛盾は転記しない**（逆回転の相対速度／『質問箱ワークフロー仕様書』§1）。
  台帳では**誤りの側が多数派**であり、機械的に運べば誤りが正本に化ける。
  正しいのは2026-08-18の側である
- **製品名の断言を、ロックチップとメインブレードへ機械的に割り振らない。**
  台帳は製品名で書かれており、分解されていない（例：ラグナレイジ＝ロックチップ「ラグナ」＋
  メインブレード「レイジ」）。どちらの性質かの切り分けは主張ごとに人間が判断する。
  契機：2026-09-17、ティガレイジの回答準備で「レイジ」がラグナレイジと同一のメインブレードだと
  `parts.csv` 照合で判明し、台帳21件が転用候補になった。一方でロックチップ側の性質は1件も
  分離できず、CEOの一次情報で埋めるほかなかった

## 3. 素材

- 入力は3種とする：**YouTubeのURL**（字幕を自動取得）／**テキストの貼り付け**（海外フォーラム・
  レビュー記事）／**公式スペック・商品情報**（一次ソース）
- **YouTubeの取得は `ベイブレードAI/tools/yt_transcript.py` が取る字幕テキストに限る。
  音声認識は使わない**（`ベイブレードAI/CLAUDE.md` の固定方針）。
  固有名詞の誤認識は `tools/terms_manual.json` の辞書で直す
- **素材は捨てない。** `ベイブレードAI/lab/materials/<日付>_<出典>.md` に原文・出典・
  該当タイムスタンプを残す。後から「独立した2ソースで一致したか」を判定するために要る
- 出典の書式：`【未確認（YouTube: <動画ID> <時刻> ／ <投稿者> ／ <公開日>）】`

### 3.1 パーツ・動画調査プロトコル【v1.2新設】

- **国内／海外を必ず分けて提示する。** YouTube動画・記事等を調査する際は「国内（日本語）」
  「海外（英語・多言語）」を明確に分けてリスト化する。海外限定パーツ（例：VALOR BAISON）は
  海外のみ、国内発売済みパーツは両方を必ず確認する。国内・海外で言及の厚さや着眼点が異なる
  傾向があるため、その差自体も分析コメントとして添える
- **動画とテキスト（ブログ・Wiki）は情報源として明確に分離してリスト化する。** 特に指示がなくとも、
  動画とテキスト記事は性質が異なる情報源として区別し、求められれば別々にも出し分けられるよう、
  調査時点から分けて記録する
- **目標件数に届かない場合、水増しせず実数のみ提示する。**「10本ずつ」等の指示があっても、
  実際に検索で確認できた件数が下回る場合は水増しせず、確認できた本数のみ提示し
  「○件のみ確認できました」と明記する。特にビット・アシストブレード単体など、ブレードに比べて
  動画露出が薄いテーマではこれが常態化しやすいことを前提に対応する
- **リストアップした時点では全て【未確認】として扱う。** 一次ソース（動画本体・記事本文）を
  Kamen Aとして直接視聴・検証していない限り、確度ラベル運用（§2）上は全て【未確認】である旨を
  毎回明記する

## 4. CEOに止めて確認すること

直接更新が既定であり、止めるのは次の4つだけとする。

1. 既存の記述と**矛盾する**観察が出たとき
2. 【仮説】以上へ**昇格**させるとき
3. パーツの**実在・表記**が `parts.csv` と食い違うとき（同仕様書§1 ①.0.4の事故経路）。
   **ユーザー入力（画像OCR含む）由来のパーツ名が一次ソースで確認できない場合も同様に扱う**【v1.2新設】。
   断定・黙って解釈変更せず、「確認できなかった」事実と考えられる可能性（表記揺れ・開発中コードネーム・
   記憶違い等）を提示してCEOの判断を仰ぐ。発売前の告知情報（大会公式ページ等）と発売後の最終製品情報とで
   名称が異なるケースがあるため（例：CX CUP告知時の仮称→発売時の正式名）、年月が離れた2情報源間の
   矛盾は常に意識する
4. **新規テーマの調査に着手する前**、note.com/kamen_aの既出記事と内容が重複・矛盾しそうなとき
   【v1.2新設】。進行するか確認してから続ける

## 5. 禁止事項

- **パーツDBの研究段階の観察を断言台帳に入れること。** 台帳は公開した回答・記事由来の断言を
  記録するもので、研究段階の観察とは別物である。混ぜない
  - **【2026-09-18改定】全面禁止から条件付き許可に変えた。** 許可されるのは
    **既存行の訂正・失効**と**一次ソースで裏の取れた事実**だけであり、
    **【未確認】【物理推論】【仮説】は台帳に入れない。** 手続きは§6に定める
- 出典を書かずに「観察」へ追記すること
- 公称スペックを推測で埋めること
- 移送済みの本文を要約・言い換えすること。**仮面Aの文体でCEOが確定させた既存資産である**

## 6. 断言台帳への反映【2026-09-18新設】

**パーツDB→断言台帳の方向を、条件付きで開いた**（2026-09-18・CEO判断）。
契機：パーツDBの全件転記の過程で、**台帳側の誤り・失効・重複が7件以上見つかった**が、
§5が全面禁止だったため直す経路が無かった。

### 6.0 大原則——研究の観察は台帳に入れない

**開いたのは「台帳自身の記録の保守」であって、「研究成果の投入」ではない。**
§5の趣旨（二次情報が正本に化けるのを防ぐ）は変えていない。

| 種類 | 台帳へ | 理由 |
|---|---|---|
| **既存行の訂正・失効・重複削除** | **可** | 台帳自身の記録の保守。新しい主張を足さない |
| **一次ソース（公式スペック・実測）で裏の取れた事実** | **可** | 【確認済み（出典）】が付く。研究段階の観察ではない |
| **物理法則だけで符号が決まる誤りの指摘** | **可** | 反証可能で、観測者に依存しない |
| 【未確認】（YouTube・レビュー・フォーラム） | **不可** | §2の上限。台帳に入れると質問箱§1①-cが正本としてgrepする |
| 【物理推論】【仮説】 | **不可** | 同上。パーツDB側に置いたままCEO判断を仰ぐ |

### 6.1 手続き——確度ラベルではなくCEO承認をゲートにする

パーツDBは§2でラベルをゲートにしているが、**台帳への書き込みはCEO承認をゲートにする。**
台帳は質問箱フローの正本であり、事故が公開文に直結するためである。

1. 研究室が矛盾・誤り・失効を見つけ、**パーツDB側の「未解決」に判定として記録する**（§4）
2. **物理的妥当性と出典の格を検討し、訂正案を作る**
3. **CEOに提示する。** 対象行・現在の記述・訂正後の記述・根拠・妥当性の自己評価を並べる
4. **CEOが承認した行だけ**、`ledger.py revise`（§6.3）で反映する
5. **承認前の送信は行わない。** ハッシュはCEOがそのラウンドで提示した値をそのまま使う。
   **自分で計算した値を渡すのは承認ゲートの自己バイパスである**（『質問箱DB反映仕様書』絶対条件A）

### 6.2 循環参照の禁止【最重要】

**この方向を開いた副作用として、循環参照の経路が生まれた。**
§2.1は台帳→パーツDBの転記を認めており、§6は逆を認める。
**放置すると、パーツDB由来の記述が台帳を一周して「独立した出典」に化ける。**

- **台帳に書き込んだ行の備考には `[parts_db由来]` と反映日を必ず残す**（機構で付与する・§6.3）
- **備考に `[parts_db由来]` を含む行は、§2.1の転記対象にしない。**
  パーツDBに既にある記述が戻ってきただけであり、**新しい裏付けではない**
- **`[parts_db由来]` の行を「独立した2ソース」の1つに数えない**（§2の【仮説】昇格条件）

### 6.3 revise 操作

`ledger.py revise` は既存行を訂正する。`apply`（新規追記）とは別の操作である。

| op | 動作 | 危険度 |
|---|---|---|
| `annotate` | **備考に追記するだけ。** 断言とラベルは触らない | 低 |
| `expire` | 備考に `【失効】` と理由を追記。**断言は残す**（監査のため消さない） | 低 |
| `correct` | 断言・ラベルを書き換える。**旧文を備考に必ず退避する** | 高 |
| `delete_dup` | 重複行を削除する。**残す行の番号を必ず指定させる** | 高 |

**安全装置（機構側で強制する）**

- **`row` だけでなく `expect_claim_head`（現在の断言の先頭20文字以上）を必ず送る。**
  一致しなければ**何も書き込まない**。台帳の行番号は位置依存であり、
  行が挿入されればズレるため、行番号だけを信頼してはならない
- **`correct` は旧断言・旧ラベルを備考に退避してから書き換える。**
  台帳は監査記録であり、原文を失ってはならない
- **全件成功か全件不実行。** 1件でも検証に落ちたら何も書き込まない（`apply` と同じ）
- **ハッシュ検証と24時間の二重送信防止は `apply` と同じ**
- **`delete_dup` は同一内容であることを機構側でも照合する**（断言・ラベル・出典記事・公開日の完全一致）

## 7. 本仕様書の範囲外

- ブレードマニュアルの執筆。研究ノートはブレードにも広げるが、**記事としての執筆は
  材料が揃ってから別途判断する**（2026-09-17・CEO判断）
  - **「パーツマニュアル」はパーツDBそのものを指す**（2026-09-17・CEO判断）。
    旧 `ビットマニュアル_v3.md`／`ラチェットマニュアル.md` の後継として別の成果物を作る計画は無い。
    旧2本が壊れたのは順位を骨格にしたからで（上位13ビット止まり・新パーツを追記できない）、
    parts_db は1パーツ1ファイルでこの構造的欠陥を持たない
- CEO自身の実測データの取り込み。一次ソース扱いになるため、入れる場合は確度ラベルの扱いを別途定める
- 改定履歴 → 『質問箱ワークフロー_改定履歴』に一本化する

**本仕様書は敵対レビュー用Gemの知識ファイルに登録しない。**
