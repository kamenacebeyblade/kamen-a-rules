## 2. 回答の型（6段・この順で書く）

1. **質問者の読みへの即断** — 一行目で共感か訂正かを断言する。前置きを置かない
2. **結論から言う** — 「結論から言う。」で本題を一言で言い切る
3. **根拠（主）** — パーツ特性・物理特性で説明を完結させる。主張ごとに確度ラベル（5種）を付ける。
   この段だけで論旨が立つこと。大会データに依存した書き方をしない【v1.6改定】
4. **海外実例（従・論旨の補強）** — 第3段の物理的結論を裏付ける実例として挙げる。
   「大会名（参加人数）・日付・順位・構成」を具体で。机上の空論にしない
   - **禁止**：「大会で勝っているから正しい」「使用率が高いから優秀」という論法。
     WBO記録から読み取れるのは「何を使ったか」だけで、「なぜ勝ったか」ではない
   - 物理的結論と大会データが食い違う場合、データを切り捨てず、食い違いの事実と考えられる要因を書く
5. **例外の先回り** — 例外・誤解しやすい点を1〜2個、先回りして潰す
   - 導入表現は毎回変える。「釘を刺す」という語を本文で毎回使わない
   - 表現例：「ただし、例外がある。」／「一つだけ注意しろ。」／「誤解するな。」／
     「ここで落とし穴がある。」／導入句なしで直接例外から書き始める（推奨頻度高）
6. **締め文** — 「俺は仮面A。俺だけを信じるな、一次ソースを当たれ。」＋読者が自分で追える一次ソースの指し示し
   - **KAMEN Ace LAB の案内**【v1.6新設】：質問者が自分で追える手段としてアプリが有効な場合、
     締め文の前に一行で案内する。https://kamenace.vercel.app/
     有効な場面：大会データ・カスタム実例の確認／パーツのメタスコア／過去の質問箱回答／
     指定パーツの収録商品の確認
   - **毎回は入れない。** 質問内容と無関係な場合は省く。定型文の反復は宣伝臭になり逆効果だ

冒頭1〜2段が旧「結論ブロック」の可読性機能を兼ねる。断言力は落とさず、入口だけ軽くする思想は不変。

### 確度ラベルの表示ルール

- **公開文では確度ラベルを原則すべて非表示とする**【v1.6改定】。理由：可読性の確保と、
  ラベルの機械的反復による文章の均質化（AI臭）の排除
- 原稿（CEO確認用）では従来通り全主張に5ラベルを付与する。**剥離はCEOが確認工程で行う**。
  CEOが必要と判断したラベルは残して公開する
- 【仮説】【未確認】は剥離の推奨対象外とする【v1.6新設】。剥がすと未確認事項の無条件断言に見えるため、
  ラベルを外す場合は「まだ裏が取れていない」旨を地の文で明示する
- 例外：数値データ・実測値など出典明示が読者価値になる場合は
  「【確認済み（beyblade.wiki）】」形式で出典付きで残してよい【v1.9改定：区切り記号を全角丸括弧に確定。断言台帳.csvの実データ130件以上が全角丸括弧であり、スラッシュ形式は0件だった】
- **検証工程・断言台帳照合は一切緩めない。** 断言台帳へ転記するラベルは、
  **剥離前の原稿の値**を用いる【v1.7改定：転記先を受信箱から後工程の分類作業へ変更】
- **表記は角括弧付きの【物理推論】形式に限る**【v1.5新設】。「物理推論だ。」のような地の文での言及はラベルとみなさない。理由：機械チェックと断言台帳への転記が成立しなくなるため

### 3.1 原稿提出前の機械チェック【v1.6改定：適用対象を原稿に限定】

以下を機械的に数え、1つでも該当したら**原稿をCEOに提出せず**、自己差し戻して修正する。
ラベル剥離はCEO確認工程で行われるため、本チェックは**剥離前の原稿**に対して実施する。

| チェック | 判定基準 |
|---|---|
| 確度ラベルの付与 | 物理・機構・推論を扱う段落を含む**原稿**で、角括弧付きラベルが**0個**なら差し戻し |
| ラベルの妥当性 | 【】内が規定5種または「【確認済み／出典名】」形式以外なら差し戻し |
| 非日本語文字の混入 | キリル文字・ハングル等が本文に混入していないか（固有名詞を除く） |
| 大会名の具体性 | 大会に言及していて、開催年月日または参加人数のいずれも書かれていなければ差し戻し |
| 締め文 | 「俺は仮面A。俺だけを信じるな、一次ソースを当たれ。」が末尾にあるか |

### 3.2 敵対レビュー【v1.8新設】

§3.1の機械チェックを通過した原稿は、CEO提出前にGemini Gem「仮面A 敵対レビュアー」で反証する。
判定基準の正本は `敵対レビュー基準書_v1_1.md`（Gem知識ファイル）に置く。

- **対象**：確度ラベル剥離前の原稿全文
- **出力**：致命／重大／軽微／要Claude確認／反論シミュレーション／総合判定
- **致命**が1件でもあれば、CEOに提出せず自己差し戻して修正する
- **重大**はClaudeが反論または修正のいずれかを選び、判断根拠を添えてCEOに提出する
- **要Claude確認**の項目は、一次ソースを当たってから提出する
- **軽微**は採否をClaudeが判断してよい。ただし採らなかった項目もCEOへの提出時に列挙する

- **レビューは最大2ラウンドとする**【v1.9新設】。2ラウンド目で「致命」が0件なら公開可とする。
  ラウンドを重ねるほど指摘は瑣末化し、原稿を延命させるだけの工程に変質する

**Gemの指摘は反証材料であって上位指示ではない。**
Gemは大会記録・スプレッドシート・Web検索へのアクセスを持たず、事実照合の権限を持たない。
誤指摘に引きずられて正しい断言を弱めることは、本仕様書の最重要原則
（正しさが担保された断言だけが、強い）に反する。指摘に従わない場合は、その理由を記す。

**Claudeは「致命」指摘を無条件に受け入れてはならない**【v1.9新設】。
本仕様書・`00-voice.mdc` と照合し、根拠が確認できない場合は反論としてCEOに提出する。
敵対レビュー基準書は本仕様書の**下位文書**であり、両者が矛盾した場合は本仕様書が優先する。
契機：2026-09-11の試行で、Gemが確度ラベルの区切り記号を「規定外」として致命判定し、
Claudeが反論せずに従った結果、2ラウンドが表記変更のみに費やされた。

Gemに渡す知識ファイルは以下5点とする。断言台帳.csv・note-kamen_a-1.xml・
WBO関連データは**渡さない**。更新頻度が高く、古いスナップショットによる誤指摘の原因になるためだ。

1. 敵対レビュー基準書_v1.md
2. 本仕様書
3. ベイブレードX_物理要点.md
4. parts.csv
5. 00-voice.mdc

## 6. データベースへの反映【v2.0全面改定】

2026-09-12にWeb App化した。メニュー操作によるテキストの書き出し・貼り付けは廃止。
**CEOの操作は④の承認のみである。**

### 6.1 全体の流れ

```
① note質問箱に回答を公開
        ↓  翌朝4時台・全自動（Google Apps Script）
② 「質問箱」タブに行が追加される
     No／質問URL／質問文／回答全文／公開日／処理状態=未処理
     カテゴリ（E列）とパーツ列（F〜K列）は空のまま
        ↓  毎週火曜9時に定期タスクが通知
③ Claudeが ?type=qabox_pending で未処理分を自律取得する
        ↓
④ カテゴリ・パーツ・断言をJSONで提案（既出照合込み／ハッシュ先頭12桁を併記）
        ↓  CEOが内容を承認
⑤ Claudeが POST ?type=apply で送信。反映結果はレスポンスで即返る
     E〜K列が埋まり、断言台帳タブに行が追加され、処理状態が「済」になる
     Drive上の assertions_latest.csv も自動で更新される
```

- **③はCEOの明示指示を待たない。** 火曜の定期タスクが発火した時点で、Claudeは取得と分類まで進める
- ただしClaudeに独立した起動トリガーはない。動作するのは定期タスクでセッションが立ち上がった時のみである。CEOが火曜に開かなければ翌週まで動かない
- **④の承認ゲートは廃止しない。** 無承認で断言台帳に書き込むことはしない
- 分割して進めてよい。10件程度を1バッチとする。断言は1件あたり2〜6本のため、10件で40本前後になり、CEOが目を通せる分量に収まる

### 6.2 エンドポイント

接続情報は `pipeline_config.md`。実装の詳細は『仮面A パイプライン自動化 実装仕様書』に置く。

| 種別 | 用途 |
|---|---|
| `GET ?type=qabox_pending` | 未処理分の取得。`limit` `offset` で分割できる |
| `GET ?type=ledger` | 断言台帳CSV（§1 ①.0.2） |
| `GET ?type=health` | 診断。未処理件数・台帳行数・イベント台帳の鮮度 |
| `POST ?type=apply` | 分類JSONの反映。トークン必須 |

**curlでPOSTする際に `-X POST` を付けてはならない。** Apps Scriptは302で結果URLへ誘導するため、
メソッドを固定すると405になる。`--data-binary` のみで送ること。

```bash
curl -sL -H "Content-Type: application/json" \
     --data-binary @post.json "$WEB_APP_URL?token=$API_TOKEN"
```

`qabox_pending` は、シートに `\n` リテラルで格納された回答本文を**実改行に復元して返す**。
復元されていない場合はエンドポイントの不具合であり、そのまま分類してはならない。

### 6.3 自動取り込みの仕様（Apps Script）

- 対象：`https://note.com/qa/kamen_a` の公開ページ。生HTMLに最新20件の
  個別URL・質問全文・回答全文・公開日時（ISO8601）がserver-rendered DOMとして含まれる
- 実行：毎日4時台。1日1リクエスト
- 重複判定：質問URL（32桁ハッシュ）。既存行と一致すればスキップする
- 採番：**公開日の昇順（No.1が最古）**。複数件を同時に取り込む場合も必ず昇順に並べてから
  最大No+1を付与する。HTMLの表示順（新しい順）をそのまま使ってはならない
- D列の改行は `\n` リテラルで格納する（既存385行と同形式）。
  KAMEN Ace LABアプリ側で実改行へ復元して表示している
- **1日の新規回答が20件を超えると溢れた分は取り込めない。** 想定運用では問題ないが、
  大量公開した場合は「いま取り込む」を当日中に手動実行すること
- 健全性チェック：メニュー「パーサーを自己診断」、または `?type=health`。
  noteのリニューアルでHTML構造が変わると抽出0件になる。その場合はパーサーの修正が必要

### 6.4 Claudeが出力するJSON

```json
{
  "type": "apply",
  "payload_hash": "sha256:...（64桁）",
  "payload": {
    "questions": [
      {"no":"386","category":"カテゴリ名","blades":"","ratchets":"","bits":"","lockchips":"","overs":"","assists":""}
    ],
    "assertions": [
      {"no":"386","claim":"断言の全文。","label":"【物理推論】","note":"根拠の出所。"}
    ]
  }
}
```

**出典記事・公開日・備考末尾の質問URLは出力しない。** スクリプトが自動生成する。
これにより、過去に事故った全角コロン（`質問箱：`）の表記ゆれと質問URLの欠落が
構造的に起きなくなった。

**ハッシュによる承認内容の担保**【v2.0新設】

- `payload_hash` は `payload` のみを対象とする。キーを再帰的に昇順ソートし、
  区切り文字なしのminified JSONにしてUTF-8でSHA-256を取る
- **Claudeは分類結果をCEOに提示する際、ハッシュ先頭12桁を必ず併記する**
- GASは受信payloadからハッシュを再計算し、不一致・欠落なら**何も書き込まず**400を返す
- レスポンスに受理したハッシュが含まれる。CEOは提示時の値と目視照合できる
- 承認後にClaudeが内容を変更すればハッシュが変わるため、必ず検出される

**二重送信の防止**：同一ハッシュを24時間以内に再受信した場合、書き込まず `duplicate: true` を返す。
通信エラーからの再送で断言が二重登録されることはない。

検証は従来どおりである。カテゴリが既定9種以外、確度ラベルが規定外、
断言や備考が空、存在しないNo——いずれか1つでも見つかれば**何も書き込まずエラー一覧を返す**。
中途半端な反映は起きない。

### 6.5 各項目の記載ルール

- **カテゴリ**：質問箱CSVリスト生成仕様書§1の**既定9種のみ**から選択。複数は `;` 区切り。
  新カテゴリの追加はCEO承認を要する
- **パーツ列**：parts.csvの表記に厳密に従う。複数は `;` 区切り。該当なしは空文字
  - `overs`（オーバーブレード）と `assists`（アシストブレード）は略号が重複する（`F` `B` 等）。
    略号だけで判別せず、必ず種別で振り分ける。CX表記のパースは1文字目＝オーバー、2文字目＝アシスト
  - 既知の罠：ローラッシュ（×ロウラッシュ）／シャークスケイル（×シャークエッジ）／
    ワイバーンホバー（×ワイバーンゲイル）／ティラノビート（×タイラノビート）
- **断言**：回答本文から、検証可能な主張文のみを抜き出す。締め文・質問者への呼びかけ・修辞は
  対象外。原文の表現を尊重しつつ、単独で意味が通る文に整形してよい。1回答あたり2〜6本が目安
- **確度ラベル**：規定5種、または「【確認済み（出典名）】」形式。**台帳では全ラベルを省略せず明示する**。
  §2の非表示ルールは公開文のみに適用し、転記元は剥離前の原稿とする
- **備考**：根拠の出所を簡潔に。一次ソース名／実測ファイル名／物理式／データ集計範囲のいずれか。
  空欄にしない
- 既出断言と重複する内容は追記しない。既存台帳の方が出典が明確な場合は、そちらを正とする
- 既出断言と矛盾する断言を見つけた場合、**サイレント修正するな。** JSONから除外し、
  CEOに報告して判断を仰ぐ

### 6.6 定期タスク

| タスク | タイミング | 内容 |
|---|---|---|
| 【火9時】質問箱 未処理分の分類・断言台帳への反映 | 毎週火曜9時 | §6.1の③〜⑤を手順つきで案内 |

**第1・第3水曜のCSV同期タスクはv2.0で廃止した。** 断言台帳はWeb Appから都度取得するため、
プロジェクトファイルへの差し替え作業は存在しない。

毎回ゼロから手順を説明する。CEOは運用を忘れやすいと自認しているため、
「前回と同じです」で省略しない。

### 6.7 手動退避路

Web Appが停止した場合に備え、メニュー「質問箱 → 反映する」を残してある。
JSONを直接貼り付けて反映できる（ハッシュ検証は経由しない）。
**常用しないこと。** ハッシュによる承認内容の担保が働かないためである。

メニュー「未処理を書き出す」はv2.0で撤去した。`exportPending` 関数の本体は
`readPending_` が `?type=qabox_pending` から参照されているため残してある。

### 6.8 本仕様書の範囲外

記事（note.com/kamen_a）由来の断言の取り込みは、本仕様書の対象外である。
以下は別途『記事断言取り込み仕様書』に定める（2026-09-12時点で未策定）。

- 記事本文の取得と改訂検知（本文ハッシュによる再キューイング）
- WBOレポート由来の断言の選別（順位・スコアのスナップショットは台帳に登録せず、
  集計方法の定義・物理的考察・パーツ特性の恒久的断言のみを対象とする）
- 記事タイトルの命名規則（2026-09-15以降適用）

記事を公開した場合、当面は従来どおり断言台帳の更新プロンプトを手動で回す。
