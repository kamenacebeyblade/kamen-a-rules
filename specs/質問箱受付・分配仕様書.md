# 質問箱受付・分配仕様書 v1.2
改定：2026-09-17（v1.2：「研究室待ち」の条件を「回答の核になるパーツに材料が無いとき」へ精緻化）

note質問箱に届いた質問を、回答制作に入る前に**受け付け・分類し、順序を決める**工程は本仕様に従う。
回答そのものの制作工程（情報取得・回答の型・チェック・承認）は『質問箱ワークフロー仕様書』に定める。

契機：未回答が約30件滞留した一方で、未回答の質問はnoteの管理画面にしか存在せず、
スプレッドシートの質問箱タブは公開済みの回答しか持たなかった。
横断的な状況を持つ場所が構造的に無く、並行作業が成立しなかった。

---

## 1. 正本の分界

| | 正本 |
|---|---|
| 横断の段階・分類・優先度・束ね | **質問箱ボードの `db`**（Artifact） |
| 質問文の原本 | `tasks/<id>/question.md` |
| タスク内の進捗（round／validate試行） | `tasks/<id>/state.json` |
| 原稿 | `tasks/<id>/draft_r0.md`／`final.md` |
| 公開済み回答・断言台帳 | スプレッドシート |

- 段階が「草案」以降のとき、ボードの `stage` は `state.json` の `status` から導出する。
  **食い違ったら `state.json` を正とし、ボードを直す。**
- 原稿の本文はボードにも写す。CEOが端末で読み、Gemへ貼るためである。
  **ディスク側が正本であり、ボードの写しを編集しない。**
- **質問文をボードだけに置いてはならない。** `tasks/<id>/question.md` に落とす規定
  （『質問箱ワークフロー仕様書』の運用）は変更しない。ボードは `db` の可用性に依存する。

## 2. 受付

- CEOはボードの投入フォームに質問を貼る。固定書式と生の質問文の両方を受け付ける。
  複数件は `---` の行で区切る
- 投入された質問は段階「受付」に入り、**分類は空のまま**置かれる
- Claudeは、PCのセッションで「受付」を拾い、`tasks/<日付>_<スラッグ>/question.md` を作って
  **原文を一字一句そのまま**保存し、分類を付けて「分類済」へ送る
- **受付の判定は質問文だけで行う浅い判定とする。** 断言台帳grep・過去回答検索はここでは走らせない。
  30件分を引くとコンテキストが持たないためである。
  正式な確定は着手時に『質問箱ワークフロー仕様書』§1の情報取得で行い、
  そこで重量クラスや分類が変わったらボードを書き換える。
  同仕様書§3.3の「途中からの切り替えは事故ではなく正常な運用」と同じ扱いとする

## 3. 分類

| 記号 | 名称 | 判定 |
|---|---|---|
| `A1` | 即答可・軽量 | 『質問箱ワークフロー仕様書』§3.3の軽量4条件をすべて満たす |
| `A2` | 即答可・標準 | 意図も情報も足りるが標準工程が要る |
| `B1` | 確認要・意図不明 | 何を聞かれているか確定できない |
| `B2` | 確認要・情報不足（質問者に聞く） | 使用パーツ・対戦環境・レギュレーション・年齢層など、質問者しか持たない情報 |
| `B3` | 確認要・情報不足（CEOが持つ） | 大会の内訳・実測値・未公開情報。同仕様書§1③のCEO請求に該当 |
| `C` | 束ね・記事化候補 | 他の質問と1本にまとめる |
| `D` | 保留 | 回答しない／時期を待つ |

**迷ったら `A2` とする。** 軽量だと判断する材料が揃わないうちに `A1` を付けない。

### 3.1 「研究室待ち」へ送る条件【v1.1改定】

次の**両方**を満たすときだけ送る。

1. 対象が**発売後3ヶ月以内または未発売**のパーツである
2. **回答の核になるパーツ**について、断言台帳・過去回答・過去記事（note-kamen_a-1.xml）・
   パーツDBの**いずれにも**材料が無い【v1.2改定】

**「対象パーツ全部に材料が無い」ではない。** CX系のように複数パーツの組み合わせで成立する製品では、
片方に既出の材料があっても、**その製品を差別化している側の材料が無ければ答えは立たない**。
契機：2026-09-17、ティガレイジ（ロックチップ「ティガ」＋メインブレード「レイジ」）の質問で、
レイジ側は断言21件あるがいずれもラグナレイジ文脈であり、ティガ側は全ソースで0件だった。
v1.1の「いずれにも材料が無い」では判定できなかった。

**パーツDBが `未着手` であることだけを理由に待ちにしてはならない。**
2026-09-17時点で263件中250件が `未着手` であり、それを理由にすると全質問が止まる。
パーツDBは§1①の**補助**であって、一次の参照先は断言台帳と過去記事である。

送るときは `relatedParts` に対象パーツを入れ、何を待っているかをカードに出す。
答えられない理由をボード上で見えるようにするのが目的であり、着手を遅らせるのが目的ではない。

## 4. 段階

```
受付 → 分類済 → 骨子 → 草案 → レビュー → 確定待ち → 公開済
        ├→ 確認待ち（B1/B2/B3。確認が返ったら分類済へ戻る）
        ├→ 研究室待ち（パーツDBに材料が無い）
        └→ 保留（D）
```

| 段階 | 入る条件 | 出る条件 |
|---|---|---|
| 受付 | `question.md` 保存済み・未分類 | 分類を付けた |
| 分類済 | 分類とクラスが確定・着手待ち | CEOが着手を指名した |
| 確認待ち | B1/B2/B3 | CEOまたは質問者から回答が来た |
| 研究室待ち | 対象パーツの材料が不足 | パーツDBが埋まった |
| 骨子 | 骨子をCEOに提出して停止中 | CEOが承認した |
| 草案 | `draft_r0.md` 生成・validate通過・CEO提出済み | CEOがGemへ投入した |
| レビュー | `state.json` が `reviewed_r<N>` | CEOが打ち切りを決めた |
| 確定待ち | `final.md`／`rejected.md` 済み | CEOが公開した |
| 公開済 | 公開完了 | — 以降は『質問箱DB反映仕様書』の管轄 |

- **段階はCEOとClaudeの両方が動かす。** CEOはボード上でドラッグし、Claudeは進捗に合わせて書く
- **着手の指名は `nominated` フラグで行う**【v1.1新設】。段階を「骨子」へ動かすことで指名しない。
  「骨子」は*骨子を提出して停止中*を意味するため、まだ骨子が無い段階で使うと状態を偽る。
  指名の経路は2つあり、どちらでもよい：
  - **Claude Codeで口頭指名する**（「◯◯を進めて」）。最速
  - **ボードで「▶ 次はこれに着手する」を押す**。外出先でも決められる。
    Claudeは作業開始時に `nominated == true` を拾う
  指名されたカードは列の先頭に出る。着手済みの段階へ動いた時点でフラグは自動で下りる
- **敵対レビューの往復はラウンド番号で突き合わせる**【v1.1新設】。
  CEOが指摘を渡すと `reviewRound` が進み、Claudeが評価を返すと `reviewAnsweredRound` が追いつく。
  差があるあいだをボードは「評価中」として表示し、CEO側の送信ボタンを伏せる。
  **Claudeは評価を返す書き込みで `reviewAnsweredRound` を必ず `reviewRound` に揃える。**
  揃え忘れると、CEOからは評価が永久に返ってこないように見える。
  指摘の本文は `reviewNotes` に残るため、`/clear` しても失われない
- **草案以降の同時進行に件数上限は設けない**（2026-09-17・CEO判断）。
  詰まりはボードの段階別件数で見る
- 「骨子」「草案」「確定待ち」で停止する承認ゲートは『質問箱ワークフロー仕様書』のものであり、
  本仕様は**ゲートを一つも減らさない**

## 5. 順番・束ね・記事化

**優先度はClaudeが提案し、CEOが決める。** 提案の根拠は次の順で見る。

1. **鮮度** — 新製品・直近大会に依存する質問は時間で価値が落ちる。上げる
2. **滞留** — 受信から14日を超えたものは一段上げる
3. **束ね待ち** — 束ね候補が揃った時点で、そのグループ全体を繰り上げる
4. **B分類は先に確認を投げる** — 待ち時間を他の作業と並行させるため、確認だけ先に出す
5. **A1（軽量）は空き時間に消化する** — 件数を減らして全体の見通しを良くする

**束ねの扱い：1本の原稿を作り、質問ごとに第1段（質問者の読みへの即断）だけ差し替える。**
『質問箱ワークフロー仕様書』§2の6段構成は、束ねても各質問の回答で維持する。

**記事化に回す場合も、各質問への回答は6段で書く。** 記事は別途作り、第6段（締め文の前）で
読者が自分で追える一次ソースとして案内する。**「記事を読んでください」だけの回答は出さない。**

**既にレビュー段階へ入っている質問を、後から束ねに巻き込まない。** 原稿の作り直しになる。
その場合は束ねず、**断言を食い違わせないための調査共有**にとどめる。

## 6. 本仕様書の範囲外

- 回答の制作工程 → 『質問箱ワークフロー仕様書』
- 公開後のデータベース反映 → 『質問箱DB反映仕様書』
- パーツDBの構造・確度の昇格規則・素材の扱い → 『パーツ研究仕様書』
- 改定履歴 → 『質問箱ワークフロー_改定履歴』に一本化する

**本仕様書は敵対レビュー用Gemの知識ファイルに登録しない。** 回答の中身を規定しないため、
登録すると誤指摘の材料になる（『質問箱DB反映仕様書』と同じ扱い）。
